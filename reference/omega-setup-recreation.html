The split: one planner, a fleet of workers

The reel's caption sums it up: “Opus plans, Haiku does the work at a fortieth of the price.” The expensive model never touches bulk work — it writes the plan, briefs each worker, and verifies results. The cheap model runs in parallel, up to dozens or hundreds of agents per run. The pricing frame from the reel is why the math works:

Why subagents carry it

“Haiku 5.5 is a fast, cost-efficient subagent for coding and well-defined tasks. A more intelligent model like Fable or Opus can plan the work and hand off subtasks to Haiku, making it practical to run many agents in parallel.”

The loop, start to finish

  1. State the goal — and what “done” means One goal at the top of the run (ship the checkout flow), with an explicit done-when (all tests pass). Everything downstream checks against it.
  2. Opus reads memory first CLAUDE.md and docs/ (progress · decisions · issues) load before planning, so the plan starts from where the project actually is. Context is managed deliberately — compact at 40%.
  3. Opus plans, briefs, and fans out The fleet launches in parallel — 16 agents in the diagram. Each Haiku worker gets exactly one job (research, build, test, review) and loads exactly one skill folder for it.
  4. Every result hits a CHECK Pass, and the work flows down. Fail, and it's sent back to the same agent on the dashed loop — the worker fixes its own work instead of the planner redoing it.
  5. Opus re-runs every check Nothing is “done” because a worker said so. The planner re-verifies the whole run against the goal before it counts.
  6. Reflect rewrites the skills After every session, the reflect/ skill rewrites the other skills with what was learned — the setup is continuously self-improving instead of frozen at however you first wrote it.

Set it up: starter files

The folder system from the diagram, as files you can drop into a project. Worker definitions live in .claude/agents/ pinned to model: haiku; the planner session runs Opus and reads CLAUDE.md first.

my-project / CLAUDE.md 
# Project memory — the planner reads this first

## Goal
Ship the checkout flow.
Done when: all tests pass.

## How work runs here
- The main session (Opus) plans, briefs, and verifies.
  It does not write bulk code itself.
- Workers are Haiku subagents defined in .claude/agents/
  (model: haiku). Each gets one job and loads one skill.
- Every worker result goes through a check before it counts.
  Failures are sent back to the same worker with the failure notes.
- Opus re-runs every check before anything is called done.

## State
Progress, decisions, and open issues live in docs/ —
update them as the run goes, not at the end.
my-project / .claude / agents / builder.md 
---
name: builder
description: Builds one briefed feature slice at a time
model: haiku
---

You are a worker agent. Before starting, load the skill
that matches your job (e.g. skills/frontend/).

- The brief from the orchestrator fixes your scope.
  Build only what it asks for — nothing extra.
- If a check sends your work back, fix exactly what
  the failure notes point at.
- Hand back: what changed, which files you touched,
  and how you verified it.
my-project / .claude / skills / reflect/ 
# reflect — runs after every session

Review what the fleet got wrong this session:
- checks that failed and why
- briefs that were ambiguous
- skills that sent workers down the wrong path

Then rewrite the other skill files (frontend/,
test-runner/, code-review/) so the same mistakes
don't repeat. Small, specific edits — one lesson
per change, noted in docs/.
